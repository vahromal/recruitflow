# Техническое задание: RecruitFlow

## 1. Назначение и статус

RecruitFlow — CRM/ATS для небольшой рекрутинговой команды (3–10 рекрутеров). Система ведёт
кандидатов и вакансии, показывает воронку найма (канбан), хранит активности (комментарии,
задачи-напоминания, ленту событий), считает дашборд, экспортирует кандидатов в CSV и
поддерживает требования GDPR по персональным данным.

**Статус реализации:**

- Бэкенд реализован и покрыт тестами: `pytest`, 26 тестов (auth/users, candidates, pipeline,
  GDPR).
- Фронтенд готов: React + TypeScript + Vite + Mantine 8, типизированный API-клиент,
  хук авторизации, страницы (дашборд, кандидаты, карточка кандидата, вакансии, канбан,
  пользователи), базовые vitest-тесты; `tsc` и `npm run build` проходят.

## 2. Роли и доступ

| Роль | Код | Права |
|---|---|---|
| Администратор | `admin` | Полный доступ: все кандидаты и вакансии, управление пользователями, экспорт, удаление, GDPR |
| Рекрутер | `recruiter` | Работает только со своими кандидатами и вакансиями (созданными им), может экспортировать и удалять своих кандидатов, выполнять GDPR-запросы по своим кандидатам; управлять пользователями не может |

Правила доступа сосредоточены в `backend/app/core/permissions.py`:

- права на действия — `ROLE_PERMISSIONS` / `check_permission`;
- доступ к объекту — `check_owns_or_admin` (админ проходит всегда, рекрутер — только если
  `owner_id` совпадает с его `id`);
- список кандидатов и вакансий для рекрутера фильтруется по `owner_id` на уровне запросов
  (`candidate_service._visible_q`, `jobs._visible_vacancy_q`).

Аутентификация: JWT (HS256, срок жизни 12 часов), пароли — bcrypt. Логин — по email и паролю,
email приводится к нижнему регистру. Деактивированный пользователь (`is_active = false`) не
может войти и не проходит проверку токена.

## 3. Функциональные требования

### 3.1. Кандидаты

Карточка кандидата содержит:

| Поле | Тип / ограничение |
|---|---|
| `full_name` | строка, обязательно, до 255 символов |
| `phone` | строка, до 50 символов; нормализуется до цифр |
| `email` | валидный email, до 255 символов; хранится в нижнем регистре |
| `city` | до 128 символов |
| `position` | должность, до 255 символов |
| `company` | текущая компания, до 255 символов |
| `expected_salary` | целое ≥ 0 |
| `source` | источник (например, `hh.ru`), до 128 символов |
| `profile_links` | JSON-список ссылок на профили |
| `telegram` | текст, до 128 символов |
| `whatsapp` | текст, до 128 символов; нормализуется до цифр |
| `notes` | свободный текст |
| `tags` | JSON-список тегов |
| `owner_id` | ответственный рекрутер (владелец), назначается текущим пользователем при создании |
| `resume_path`, `resume_filename` | путь к файлу резюме и исходное имя файла |

Требования:

- **Создание/редактирование/удаление** кандидата; редактировать и удалять может владелец или
  администратор.
- **Резюме**: загрузка файлов только `.pdf` и `.docx`, размер не более `MAX_UPLOAD_SIZE_MB`
  (по умолчанию 10 МБ). Файл сохраняется в `STORAGE_LOCAL_PATH/resumes`
  (`/data/uploads/resumes` в Docker) под именем `cand_<id>_<hash>.<ext>`; при повторной
  загрузке старый файл удаляется. Доступно скачивание с исходным именем. При удалении
  кандидата файл удаляется с диска.
- **Поиск и фильтры**: `q` ищет по ФИО, email, телефону, должности, компании и городу;
  отдельные фильтры — `city`, `position`, `source`, `tag`, `owner_id` (последний учитывается
  только для админа). Пагинация: `page`, `page_size` (по умолчанию 20, максимум 100).
  Сортировка — по `updated_at` (сначала свежие).
- **Дедупликация**: проверка по email (без учёта регистра) и телефону (только цифры).
  При создании или изменении кандидата с совпадением возвращается `409` с кодом
  `duplicate_candidate` и списком найденных дублей. Отдельный эндпоинт
  `GET /api/candidates/duplicates?email=&phone=` возвращает совпадения с указанием, по какому
  полю найдено.

### 3.2. Вакансии

Поля: `title` (обязательно), `client`, `description`, `requirements`, `salary_min`,
`salary_max`, `status` (`open` / `paused` / `closed`), `owner_id` (ответственный, текущий
пользователь при создании), служебные `created_at` / `updated_at`.

Требования:

- CRUD вакансий; рекрутер видит и изменяет только свои, админ — все.
- Список с пагинацией, фильтром по статусу и поиском `q` по названию и клиенту.
- Некорректный статус отклоняется с `422`.

### 3.3. Воронка (канбан)

Стадии (порядок фиксирован в `STAGE_ORDER`):

`new` → `screening` → `interview_recruiter` → `interview_client` → `test_task` → `offer` →
`hired`, а также `rejected`.

Модель: карточка `CandidateStage` связывает кандидата и вакансию; пара
«кандидат + вакансия» уникальна (повторное добавление — `409`).

Требования:

- Добавление кандидата в воронку вакансии; начальная стадия — `new`.
- Смена стадии; для `rejected` **обязательна причина** (`reject_reason`), иначе `422` с кодом
  `reject_reason_required`. При переходе из `rejected` причина очищается.
- История смен стадий (`stage_history`): откуда, куда, комментарий, автор, дата. Запись
  создаётся и при добавлении кандидата в воронку (из `null` в `new`).
- Доска вакансии: карточки, сгруппированные по всем восьми стадиям.
- Перетаскивание карточек мышью — нативный HTML5 drag & drop на канбан-доске; API
  предоставляет операцию перемещения `POST /api/cards/{card_id}/move`.

### 3.4. Активности

- **Комментарии** к кандидату (тип `comment`).
- **Задачи-напоминания** (тип `task`): текст, дата/время `due_at`, статус `open` / `done`.
  Список «задачи на сегодня» возвращает открытые задачи с `due_at <= сейчас`, то есть
  включая просроченные, максимум 100.
- **Лента событий** (`/api/feed`): последние комментарии и задачи по доступным пользователю
  кандидатам, с пагинацией (по умолчанию 30, максимум 100).
- Список активностей кандидата с фильтром по типу и пагинацией.
- Все операции доступны владельцу кандидата или админу.

### 3.5. Дашборд

`GET /api/dashboard` возвращает:

- количество кандидатов по каждой из восьми стадий;
- количество открытых вакансий;
- количество задач на сегодня (открытые, `due_at <= сейчас`);
- общее количество кандидатов;
- статистику по рекрутерам: ФИО, число кандидатов, нанятых, отклонённых, открытых вакансий.

Рекрутер видит статистику только по себе и данные только по своим кандидатам/вакансиям;
админ — по всем пользователям.

### 3.6. Экспорт в CSV

`GET /api/candidates/export` (с необязательными фильтрами `q`, `tag`) отдаёт CSV с колонками:

`id, full_name, phone, email, city, position, company, expected_salary, source, telegram,
whatsapp, tags, created_at`

Теги объединяются через `;`. Экспорт учитывает права видимости: рекрутер получает только
своих кандидатов. Требуется право `EXPORT_DATA` (есть у обеих ролей).

### 3.7. GDPR

- **Экспорт данных кандидата** — `GET /api/gdpr/candidates/{id}/export`: JSON-файл с карточкой
  кандидата, активностями, участием в воронках и историей стадий.
- **Удаление данных кандидата** — `DELETE /api/gdpr/candidates/{id}`: удаление кандидата со
  всеми связанными записями (каскадно: карточки воронки, история, активности).
- **Ограничение доступа** — роли и проверка владения (см. раздел 2).
- В конфигурации есть `CANDIDATE_RETENTION_DAYS` (0 = выключено). Автоматическая
  анонимизация по сроку хранения в текущей версии не реализована.

## 4. Нефункциональные требования и продакшен

### 4.1. Топология Docker Compose

Продакшен-стек (`docker-compose.prod.yml`, имя проекта `recruitflow`):

| Сервис | Назначение | Порты | Том |
|---|---|---|---|
| `db` | PostgreSQL 16 | наружу не публикуется, доступен только внутри сети compose | `pgdata` |
| `backend` | FastAPI + uvicorn | только `expose: 8000` | `uploads` → `/data/uploads` |
| `frontend` | собранная статика в nginx | только `expose: 80` | — |
| `caddy` | HTTPS, reverse proxy, Let's Encrypt | `80:80`, `443:443` | `caddy_data`, `caddy_config` |

Caddy маршрутизирует `/api/*` и `/health` на `backend:8000`, остальное — на `frontend:80`.
Настройки: gzip, HSTS, `X-Content-Type-Options`, `X-Frame-Options: DENY`,
`Referrer-Policy`, скрытие заголовка `Server`, лимит тела запроса 15 МБ, JSON-логи.

### 4.2. Файлы

Резюме хранятся в именованном Docker-томе `uploads` (`STORAGE_LOCAL_PATH=/data/uploads`).
Настройка `STORAGE_BACKEND` допускает значение `s3` как точку расширения, но реализован
только `local`; архитектура хранения вынесена в конфигурацию, чтобы позже подключить S3.

### 4.3. Безопасность

- HTTPS с автоматическим сертификатом Let's Encrypt через Caddy; HTTP→HTTPS — на стороне Caddy.
- CORS ограничен списком `CORS_ORIGINS` (свой домен).
- Rate-limit входа: по умолчанию 5 попыток за 300 секунд; при превышении — `429`
  (`rate_limited`). Счётчик ведётся в памяти процесса по email и сбрасывается при рестарте.
- Порт БД наружу не открывается (в prod-конфигурации у `db` нет `ports`).
- Пароли — bcrypt; JWT подписывается `SECRET_KEY`; секреты задаются через `.env`
  (файл в `.gitignore`).
- Унифицированный формат ошибок: `{"error": {"code", "message", "details"}}`; SQL-детали
  клиенту не отдаются.

### 4.4. Эксплуатация

- **Миграции Alembic при старте**: команда контейнера backend —
  `alembic upgrade head && uvicorn ...`; при первом запуске создаётся схема.
- **Health-check**: `GET /health` → `{"status": "ok", ...}`; healthcheck есть у backend
  (curl), db (`pg_isready`) и frontend (wget).
- **Restart policy**: `unless-stopped` у всех сервисов.
- **Логи**: структурированные однострочные записи в stdout (backend), JSON-логи Caddy;
  ротация — средствами Docker log driver.
- **Бэкапы**: `deploy/backup.sh` делает `pg_dump` базы и архив тома резюме, кладёт файлы в
  `backups/`, хранит 14 дней (`RETENTION_DAYS`), пишет manifest. Запускается вручную или по
  cron.
- **Восстановление**: `deploy/restore.sh <db_dump.sql.gz> [--resumes <tar.gz>]` — сначала
  делает страховочный дамп текущей БД, затем пересоздаёт схему `public`, восстанавливает дамп
  и проверяет количество строк в `users`, `candidates`, `vacancies`.
- **GDPR**: экспорт и удаление персональных данных кандидата, ограничение доступа ролями.

### 4.5. Основные переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|

## 5. Модель данных

| Таблица | Содержимое |
|---|---|
| `users` | пользователи: email (уникальный), ФИО, хеш пароля, роль, активность, дата создания |
| `candidates` | кандидаты, владелец `owner_id`; уникальность `email` и `phone` |
| `vacancies` | вакансии, владелец `owner_id`, статус |
| `candidate_stages` | карточка воронки: кандидат + вакансия (уникальная пара), текущая стадия, причина отказа |
| `stage_history` | история переходов: `from_stage`, `to_stage`, комментарий, автор, дата |
| `activities` | комментарии, задачи (`due_at`, `task_status`) и события кандидата |

Связи: кандидат → карточки воронки и активности (каскадное удаление); карточка → история
(каскадное удаление); автор в истории и активностях при удалении пользователя становится
`NULL`; удалить пользователя, у которого есть кандидаты/вакансии, нельзя (`RESTRICT`).

## 6. API

Все эндпоинты, кроме `/health`, доступны под префиксом `/api` и требуют JWT
(`Authorization: Bearer <token>`), если не указано иное.

| Метод и путь | Назначение |
|---|---|
| `POST /api/auth/login` | вход (form-data: `username`, `password`), выдаёт токен |
| `GET /api/auth/me` | текущий пользователь |
| `GET/POST /api/users`, `PATCH/DELETE /api/users/{id}` | управление пользователями (только админ) |
| `GET/POST /api/candidates` | список с поиском/фильтрами; создание |
| `GET /api/candidates/export` | CSV-экспорт |
| `GET /api/candidates/duplicates` | проверка дублей по email/телефону |
| `GET/PATCH/DELETE /api/candidates/{id}` | карточка, изменение, удаление |
| `POST/GET /api/candidates/{id}/resume` | загрузка/скачивание резюме |
| `GET/POST /api/vacancies`, `GET/PATCH/DELETE /api/vacancies/{id}` | вакансии |
| `GET /api/vacancies/{id}/board` | канбан вакансии |
| `POST /api/vacancies/{id}/cards` | добавить кандидата в воронку |
| `GET /api/cards/{id}`, `POST /api/cards/{id}/move` | карточка и смена стадии |
| `GET /api/candidates/{id}/activities` | активности кандидата |
| `POST /api/candidates/{id}/comments` | комментарий |
| `POST /api/candidates/{id}/tasks` | задача с датой |
| `PATCH /api/tasks/{id}` | изменить задачу / закрыть |
| `GET /api/tasks/today` | задачи на сегодня и просроченные |
| `GET /api/feed` | лента событий |
| `GET /api/dashboard` | дашборд |
| `GET /api/gdpr/candidates/{id}/export` | GDPR-экспорт |
| `DELETE /api/gdpr/candidates/{id}` | GDPR-удаление |
| `GET /health` | health-check (без авторизации) |

Swagger/OpenAPI доступны в не-prod окружениях: `/api/docs`, `/api/openapi.json`. В
`ENVIRONMENT=prod` они отключены.

## 7. Тесты

`cd backend && pytest` — 26 тестов:

- `tests/test_auth_users.py` — 7: health, неверный пароль, обязательный токен, rate-limit,
  управление пользователями, дубликат email, минимальная длина пароля;
- `tests/test_candidates.py` — 10: CRUD, дедупликация по email и телефону, поиск/фильтры,
  изоляция данных рекрутера, запрет правки чужого кандидата, CSV, резюме, удаление;
- `tests/test_pipeline.py` — 7: CRUD вакансий, невалидный статус, канбан и переходы с
  историей, обязательная причина отказа, комментарии/задачи/лента, дашборд, сквозной сценарий;
- `tests/test_gdpr.py` — 2: экспорт и удаление данных.

Тесты пересоздают отдельную БД (`recruitflow_test`), применяют реальные миграции Alembic на
чистой базе и очищают таблицы между тестами.

## 8. Допущения и принятые решения

- **(а) Видимость данных.** Рекрутер видит и изменяет только собственных кандидатов и
  вакансии (по `owner_id`), администратор — всё. Совместный доступ к кандидатам других
  рекрутеров не предусмотрен.
- **(б) Нормализация телефона.** Телефон (а также WhatsApp) сохраняется как строка только из
  цифр, без `+`, пробелов и разделителей. Это делает дедупликацию по телефону надёжной:
  `+7 999 123-45-67` и `79991234567` считаются одним номером.
- **(в) Rate-limit входа.** Счётчик попыток хранится в памяти процесса и сбрасывается при
  рестарте backend. Для MVP этого достаточно; при нескольких инстансах или жёстких
  требованиях нужно вынести счётчик в Redis.
- **(г) Уникальность email.** Регистронезависимость обеспечивается на уровне сервиса: email
  приводится к нижнему регистру при создании/обновлении, поиск дублей идёт через
  `lower(email)`. Ограничение уникальности в БД (`uq_candidates_email_lower`) при этом
  регистрозависимое — оно страхует от гонок, но не заменяет проверку в сервисе.
- **(д) Frontend в продакшене.** Статика собирается в образе frontend и отдаётся отдельным
  nginx-контейнером; Caddy стоит перед ним и терминирует HTTPS, проксируя API на backend.
- **(е) Тесты фронтенда.** Для фронтенда предусмотрены vitest + testing-library (jsdom),
  покрытие базовое; основной объём автотестов — бэкенд.
- **(ж) Запуск окружений.** Dev-стек поднимается командой `docker compose up` (сборка —
  `--build`), продакшен — `docker compose -f docker-compose.prod.yml up -d --build`.
- **(з) Валидация email.** Адрес проверяется на **формат** (`name@domain.tld`, без пробелов),
  а не через `EmailStr` из pydantic. Причина: `email-validator` отвергает зарезервированные
  домены (`.local`, `.test`), из-за чего собственные учётки вида `admin@recruitflow.local`
  роняли `GET /api/users` с HTTP 500 на этапе сериализации ответа. Теперь спецдомены
  допустимы, а кривой адрес даёт штатный 422 с единым форматом ошибки (детали ошибки
  валидации дополнительно приводятся к JSON-безопасному виду, см. `core/errors.py`).
